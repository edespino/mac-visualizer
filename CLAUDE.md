# Project Guidance for Claude

This file loads automatically into every Claude session in this directory. It captures conventions, patterns, and accumulated lessons that would otherwise be re-learned each session.

## Project overview

mac-visualizer is a macOS audio visualizer that reacts to the audio of Spotify and Apple Music (the fixed target list `ProcessLocator.defaultTargets`) via a Core Audio process tap. 26 visualizer styles, multiple render modes per style, HDR-bloom pipeline, configurable trails, window transparency. Original work under Apache License 2.0 — see `LICENSE` and `NOTICE`.

**Tech stack:** Swift 5.10, Metal 3, MetalKit, MetalPerformanceShaders, vDSP (FFT), AppKit, SwiftUI, ScriptingBridge (track info), Core Audio process tap (audio capture), AVAudioEngine (Spinner hum) and RealityKit (the default Spinner renderer on macOS 15+). XcodeGen + Makefile build. macOS 14.4+ (the Spinner style needs macOS 15).

## Build and test (always)

```bash
make build              # Generates Xcode project via XcodeGen, builds debug
make test               # Runs the full XCTest suite (over 1,500 tests)
make clean && make build && make test   # Full clean rebuild
```

**Never** invoke `xcodebuild` directly. The Makefile handles XcodeGen project regeneration and the right scheme/destination flags.

CI (`.github/workflows/ci.yml`) runs `make build` then `make test` on GitHub's `macos-15` runner with the latest stable Xcode, on pushes and pull requests to `main` and `dev`. `make test` alone builds only MacVisualizerCore and the Core tests; `make build` is what exercises the app target (signing config, icon, RealityKit code).

## Architecture

- `Sources/Core/` — pure Swift, no Metal/AppKit/UI dependencies. Audio analysis, visualizer logic, settings, palettes, deterministic utilities. Lives in its own `MacVisualizerCore` framework target. Has full XCTest coverage.
- `Sources/Rendering/` — Metal renderer, MTKView wrapper, offscreen render probe, shaders. Imports MacVisualizerCore. `Sources/Rendering/RealitySpinner/` holds the RealityKit Spinner renderer (macOS 15+).
- `Sources/App/` — SwiftUI app, settings views, window configuration, RenderModel (ObservableObject driving rendering).
- `Sources/App/AcknowledgementsView.swift` — the Acknowledgements window (`Window(id: "acknowledgements")`): header strip, Credits / Third-Party Licenses / License picker, blocks rendered from the bundled `NOTICE`, `THIRD_PARTY_NOTICES.md`, `LICENSE` (parsed once by `AcknowledgementsModel`; LICENSE shown verbatim in one monospaced block). Opened from the app menu (`CommandGroup(replacing: .appInfo)`, which also supplies the About panel credits via `AboutPanel`), the right-click menu (`AcknowledgementsRouter`, same pattern as `SettingsRouter`). `InputController` monitors act on the main and Settings windows only, so keys typed there do nothing. The pure parser is `MarkdownParser` / `MarkdownInline` in `Sources/Core/MarkdownBlocks.swift` (tested). `Sources/App/AcknowledgementsProbe.swift` is the `--acknowledgements-probe <outdir>` offscreen renderer (not unit tested, like the other probes).
- `Sources/Core/HubCutMesh.swift` — `HubCutField` / `HubCutMesh` / `HubCutParams` / `HubCutStroke`: the pure, tested mesher that turns the Spinner's hub mark stroke lists into face, cut and raised hub geometry for RealityKit (see "Spinner" > "Metals, finishes, marks").
- `Sources/Services/` — Core Audio capture service, now-playing service (ScriptingBridge), LRCLIB and Gemini network clients, the Spinner hum player (`SpinnerHumPlayer`, AVAudioEngine), and the CLI probes (`AudioProbe`, `NowPlayingProbe`, `LyricsProbe`).
- `Sources/Rendering/Shaders.metal` — all Metal shaders (vertex: vs_main, fullscreen_vs; fragment: fs_main, fs_round, composite_fs, fade_fs, plasma_fs, bumpscope_fs, lavalamp_fs, voronoi_fs, octave_meatballs_fs, star_nest_fs, outrun_rain_fs, spinner_fs; RealityKit hand-off: rk_copy_fs, rk_shadow_cov_fs).
- `Tests/CoreTests/` — XCTest targeting MacVisualizerCore (Sources/Core only). Other targets are not unit-tested.

## Key types

- `AudioFrame` (Sources/Core) — per-frame audio analysis output: `bands`, `bandsLeft`, `bandsRight`, `bandPeaks`, `waveform`, `rms`, `peak`, `timestamp`, `beat`, `beatIntensity`, `bassEnergy`, `trackId`. All Float arrays, all in [0, 1] normalized except positions. `bassEnergy` is a scalar pre-gain mean FFT magnitude over a fixed ~30–150 Hz window (not normalized), feeding the lyric beat follower.
- `VisualizerStyle` (enum) — 26 cases (the last two are the Disc Spinner `.spinner` and the Tri-wing Spinner `.triWingSpinner`; `isSpinnerFamily` is true for both, `spinnerModel` is `.disc` / `.triWing` / nil). `customShader(settings:)` decides whether a style takes the vertex-emit pipeline or a fragment-shader pipeline. `makeVisualizer()` is the factory. Per-style **capability flags** drive which Settings controls are live for a style and are each unit-tested with their exact set: `supportsPositionOffset`; `usesFrequencyBands` (reads the gained/smoothed/windowed bands → governs Gain, Smoothing, FFT window; false for the waveform-only and loudness/beat-only styles — Plasma, Fireworks, Beat Counter, Oscilloscope, Polartone, XY Scope, Spinner); `usesBarCount` (Bars; = `usesFrequencyBands` minus Musical Spectrum, whose band count is fixed by its note mapping); `usesPeakHold` (Bars only); `usesStereoImage` (Bars, Radial, Ribbon Wave, Joy Plot, Heightfield, Voronoi, Lava Lamp, Iris); `usesPalette` (false only for Spinner, whose colours come from its metal: the RealityKit renderer ignores the palette for the body and the classic shader uses it for a faint tint; the flag and its exact-set test are unchanged). The Color palette control is live for the Spinner through the settings-aware `VisualizerStyle.paletteControlEnabled(spinner:)` (Core, tested): `usesPalette`, or the Spinner with the Tri-wing model and `lightColors == .palette`, because the Tri-wing's edge lights then take their colours from the palette (see "Edge lights" > Light colours). The Settings UI greys out a control (with a tooltip) when the active style's flag is false — disable, not hide.
- `Visualizer` (protocol) — `makeVertices(frame:settings:aspect:) -> [BarVertex]`. Shader-driven visualizers return `[]`; the renderer dispatches via `customShader(settings:)`.
- `VisualizerSettings` — top-level/app-wide settings; contains `profiles: [VisualizerStyle: StyleProfile]` for per-style settings. Codable with tolerant decoder. App-wide window/placement chrome lives here (NOT per-style): `overlayEnabled`/`overlayPosition`/`overlayOpacity` (track overlay), `alwaysOnTop`, `targetFPS`, `mouseControlModifier` (modifier+mouse layer: off/shift/option/command, default shift), plus the transparency fields, the window border (`windowBorderMode`: off/auto/always, + color/opacity/width), and the lyrics/palette-cycle fields. These groups were per-style before (position offset is per-style AGAIN, see `StyleProfile`); the decoder migrates them — old flat keys seed the app-wide value, and a per-style-only `settings.json` falls back to defaults once on first load.
- `StyleProfile` — per-style settings (palette, gain, bar count, smoothing, glow, render modes, `fullscreenDisplayID`, `backgroundStyle`, `positionOffsetX`/`positionOffsetY`, `enabled`, and `spinner`, a nested `SpinnerSettings` that every style carries at its defaults and only the Spinner reads). Tolerant Codable so adding fields doesn't break existing JSON. NOTE: track overlay, always-on-top and frame rate are no longer here — they moved to `VisualizerSettings` (app-wide). **Position offset is per-style** (each visualization remembers its own): `settings.positionOffsetX/Y` are forwarders to `settings.current`; use `StyleProfile.defaults(for:)` (not `.defaults`) when a style's profile is missing/reset, because Wireframe's default `positionOffsetY` is -0.07. The settings decoder no longer encodes a top-level offset; a legacy top-level `positionOffsetX/Y` (0.11-0.13 files) seeds every profile that has no offset keys of its own, per-profile values win. `wireframeVerticalCenter`/`heightfieldVerticalCenter` are separate style-specific fields and untouched.
- `BeatDetector` (Sources/Core) — adaptive onset detection. Owned by `SpectrumAnalyzer`; per-frame output attached to `AudioFrame`.
- `LyricsModel` (Sources/Core) — lyrics orchestrator for the overlay; see "Lyrics overlay".

## Lyrics overlay

Time-synced lyrics with a line-aligned English translation, drawn as a non-interactive SwiftUI layer (`LyricsOverlay`) between `MetalView` and `TrackOverlay`. Ported from the user's own `spotify-translate-lyrics` web app; this is group 1 of 5 (display only). Design: `docs/superpowers/specs/2026-11-11-lyrics-overlay-design.md`.

- **Core (unit tested):** `LyricsSettings` (app-wide, nested at `settings.lyrics`, NOT per-style), `LRCParser` + `findActiveLine`, `PlaybackPositionTracker`, `EnglishLyricsDetector`, `LyricsTranslator` (prompt, N-in N-out validation, retry, chunks of 20, rate-limit wait), `GeminiAPI` (pure request/response shaping), `LyricsCacheStore`, `GeminiKeyStore`, and `LyricsModel` (the `@MainActor` ObservableObject that orchestrates cache, fetch, detection, translation and publishes `display` + `status`).
- **English detection (skip translation):** `EnglishLyricsDetector.isEnglish` gates translation — confidently-English lyrics are never sent to Gemini and render as one centered column. It excludes cross-language-ambiguous tokens from BOTH word lists (English casual **"ya"** and the **"la la la"** vocable no longer count as Spanish evidence, mirroring the existing enWords exclusions), and has a **secondary acceptance path**: text with a real English function-word rate and ZERO foreign evidence (no Spanish stopwords or accents, and no Portuguese/Italian/French words or accents) reads as English even when it has too few distinct function words for the strict path (short/simple songs). A **third path** accepts an English-dominant song with a non-Spanish section (a French/Italian refrain or verse, e.g. "Psycho Killer"): the Spanish-only translator would mangle it, so it is shown as-is when there are MANY distinct English function words (≥10, which a foreign-language song cannot muster), a real English rate, minimal Spanish *stopword* evidence, and none of the uniquely-Spanish marks ñ ¿ ¡ (shared accents á é í ó ú, common to French/Portuguese/Italian, do NOT block it). Foreign evidence is counted, not an early reject. The **cache-load path re-runs the detector** on the cached source lines, so a song mistranslated under an earlier detector re-centers on next play without a cache wipe. Two-column layout is for a real translation only. Validated against "Espresso" (ya), "Dazz" (la), "Forever" (short/simple), and "Psycho Killer" (English + French).
- **Lookup:** `LRCLIBClient` tries the exact `/api/get` first, then `/api/search` by title and artist, choosing with `LRCLIBMatch.best` (Core, tested) which returns a `Choice` (record + `approximate`): closest duration within 3 s, synced preferred. A wider duration gap means a different recording whose timestamps may not line up. **Mis-timed records:** LRCLIB has records filed under the wrong duration (e.g. "Audition (The Fools Who Dream)": the exact 228 s match carries the 252 s film cut's timings, ~23.5 s late, last line 20 s past the track's end). `LRCLIBRecord.timingOverrunsDuration` (last timestamp > its own duration + `overrunToleranceMs`, 5 s) marks them; `best` never picks one, `exactSuffices` sends a mis-timed exact hit on to search, and `resolve` falls back to it stamped `approximate` only when search has nothing synced. `LyricsModel` refetches a non-approximate cached entry whose lines overrun the track (`linesOverrun`). A shifted record that still ends inside the track is NOT detectable.
- **Approximate matches:** with `acceptApproximateMatches` on (default) and nothing synced within tolerance, `best(allowLoose:)` accepts the closest synced recording within `looseToleranceMs` (30 s; beyond that it is a different recording and rejected), marked `approximate` through `LyricsResult.synced`. The model exposes `approximateMatch`, the Settings status line flags it, and the cache entry persists it. Out-of-tolerance synced beats exact plain (only synced scrolls). Turning the setting off skips an approximate *cached* entry and refetches strictly, so the toggle hides approximate lyrics already saved for a song, not just new ones.
- **Local `.lrc` folder:** `localLyricsFolder` (empty disables) overrides both the cache and LRCLIB. The model calls `fetcher.localOverride(...)` *before* its cache read, so a local file replaces a stale/wrong cached entry (a cached translation is reused only when its source lines match). `LocalLyricsMatcher` (Core, tested) matches a file by "Artist - Title"/"Title - Artist"/"Title" (accent- and punctuation-insensitive); `LocalLyricsReader` decodes it (`LyricsTextDecoder`: UTF-8 → Windows-1252 → Latin-1) and parses it; `CompositeLyricsFetcher` (Services) serves local via `localOverride` and LRCLIB via `fetch`, with blocking I/O off the cooperative pool.
- **Timing offset:** `timingOffsetMs` shifts the interpolated position in `activeIndex` (positive pulls lines earlier); app-wide, nudges a drifted approximate match or player latency.
- **Fetch options:** per-fetch config (`localFolder`, `allowApproximateMatch`) rides in `LyricsFetchOptions`, built by the model from settings; the model re-fetches the current track when the folder or approximate policy changes.
- **Not done (deliberately):** the Spotify internal color-lyrics endpoint. It is TOTP-gated (Spotify added it to block third-party clients and rotates it), so using it circumvents an access control, breaks Spotify's terms for the cookie's account, and breaks on every rotation. The local `.lrc` folder covers the same gap with the user's own data.
- **Song title header:** `LyricsDisplay` carries the song's `title`/`artist` (set in `LyricsModel` from the track, so each block keeps its own song during a cross-song transition). `LyricsOverlay` always renders a `LyricHeaderRow` above the lyrics as the opening "active lyric": the **italic** title (a touch larger, `otherColor`, legible — NOT the dark shadow color) over the performer, centered, pinned at the active anchor during the intro and scrolling up/off as a past line (sentinel `.id(Int.min)`) once the first lyric begins. A song with **no lyrics** (instrumental / none / fetch error) gets a **header-only `LyricsDisplay`** (empty rows, title+artist) so the song still shows; after `headerOnlyDwellSeconds` it scrolls off (drifts up + fades) via a `.task` keyed on `songKey` **and the replay nonce**, and once it is gone the overlay reports no text on screen so the **visualization recenters** (see "viz recenter" below). **Restarting the song** (replay-nonce bump) re-shows the title/performer, which then scrolls off again. There is no on/off setting — the header is always on. **Viz recenter:** `model.lyricsShowing` (which `MetalView` uses to offset the visualization below the text, gated by `centerBelowLyrics`) is driven by the overlay's *effective* text visibility via `onTextVisibleChange` — real lyrics, or a no-lyrics header that has NOT yet scrolled off — NOT merely `display != nil`, so a no-lyrics song recenters the viz once its title scrolls away.
- **Overlay transitions (all SwiftUI — validate live, not in tests):** the whole block fades in on first appearance and out on removal via `.transition(.opacity)` keyed to `lyricsShowing`; a song change crossfades old↔new via `.id(songKey)` (songKey = `title|artist|count|first|last` original text — stable across a translation arriving or the active line moving, distinct per song even with no rows); the translation column fades in when the async translation lands (per-row `hasTranslation` opacity); and the lyrics/title fade out **promptly on pause/stop** via an opacity keyed to `nowPlaying.track` (nil on pause, held across song changes), faster than the 2 s audio idle-fade, without clearing the frozen display. The corner `TrackOverlay` (in `ContentView`, outside the idle-fade group) is shown whenever a track is playing and the track-overlay setting is on, independent of the lyrics layer, so the album art and title stay on screen after the scrolling song-title header has moved off; the lyrics layer treats the card's bottom edge as its upper limit when the card is in a top corner (`topInset`).
- **Track overlay card (`TrackOverlay`, all SwiftUI — validate live):** the corner card shows the **album art** + title with the **performer alone** on the second line (Apple Music = embedded local art, immediate; Spotify = `artworkURL` fetched over the network, ~0.1–0.3 s late). It runs its own opacity lifecycle via `runFade` (a `.task(id:)` keyed to the track): **bloom** to full, hold, **settle** to `overlayOpacity`. On a song switch the old card dips out and the new one blooms in **already showing its art** — `runFade` waits (bounded) for the new cover before the swap, and the cover is held in a reference-type `ArtworkStash` so the escaping task reads it live (a `@State`/`let` read inside the task is a stale snapshot). **Gotcha:** `onChange(of: artwork)` must NEVER push `nil` — on a switch the model clears `artwork` in the same update that changes `track`, and SwiftUI can run that handler while `track` still reads as the OLD song, so a nil push blanks the still-visible old card (it goes text-only); clearing/replacing art is the swap's job. **Hovering** the card holds it at full **and enlarges it** (`hoverProgress` drives a corner-anchored `scaleEffect` up to `hoverScale`, clamped to the window width via a measured card width + `TrackOverlayWidthKey` so the grown card never spills past the far edge); the album art is **oversampled** (rasterized at the grown size, shown shrunk) so the enlarge stays crisp instead of upscaling a small bitmap. The grow (size) is always responsive and symmetric, gated only by a `transitioning` flag during the dip/swap — so catching the card mid-settle still raises it to full. **Clicking** it brings the source player to the foreground via `NSWorkspace.openApplication(at:configuration:)` with `activates = true` (the running app's `bundleURL`, else the registered URL; `NSRunningApplication.activate()` is only the no-URL fallback). That sends the reopen event, so a minimized window is restored and a closed one reopened, which plain `activate()` does not do. NOT the deprecated `NSWorkspace.open(appURL)`, which trips macOS App Management. Each click logs one `window`-category line (bundle id, was-running, completion error; no track text). **Double-click on the card does not toggle full screen:** the card publishes its on-screen rect (rest rect from a `TrackOverlayRectKey` preference in global/window space, scaled about its corner by the current hover scale; nil when no visible card) to `MainWindow.trackCardRect`, and `InputController.handleMouse` consults the pure, tested `suppressesActionOverCard` (Core) after flipping the event point to top-left origin, letting the event through untouched so the card's tap still fires. A drop shadow (opacity `0.45·level`, so it dims with the card) lifts it off the visualization. **Restart re-bloom:** `runFade` keys its `.task` on the track AND the replay nonce; a restart of the same song re-fires it via a **re-reveal path** (same song already shown → no dip/swap, just bloom-hold-settle again). The card's bottom edge is published up (`TrackOverlayBottomKey` + a named coordinate space) so the lyrics layer treats it as its upper limit and fades out before reaching it.
- **Distance fade:** `LyricsSettings.fadeLines` (0 = off) scales non-active rows by distance from the active line via `opacity(for:distance:)`.
- **Beat bounce:** the active line's drop shadow pulses to the beat. `SpectrumAnalyzer` computes `AudioFrame.bassEnergy` (a fixed ~30–150 Hz pre-gain FFT-magnitude window, independent of `barCount`/band-mapping/gain); `RenderModel` feeds it on the dsp queue to `LyricBeatFollower` (Sources/Core, unit-tested) — a dedicated adaptive, floor-free, once-per-beat onset follower, independent of the visualizers' `BeatDetector`, so it fires at the user's ~0.02 capture level where the 0.05-floor detector stays silent. Non-zero pulses publish via `RenderModel.lyricPulse` (a `PassthroughSubject<Float, Never>`) to `LyricsOverlay`, which snaps only the active line's shadow (radius/offset/opacity), never the text (no-jitter). Mode (`beatBounceMode`: off/lift/glow/both) and `beatBounceStrength` are app-wide `LyricsSettings` fields; the Settings controls disable when the drop shadow is off. Live capture only (not Demo Mode). Design: `docs/superpowers/specs/2026-11-17-lyric-beat-bounce-design.md`.
- **Services:** `LRCLIBClient` (`LyricsFetching`) wrapped in `CompositeLyricsFetcher` with `LocalLyricsReader`, `GeminiProvider` (`TranslationProvider`), `LyricsProbe` (`--lyrics-probe`).
- **App:** `LyricsOverlay`, `LyricsSettingsSection`. `LyricsCoordinator` (owned by the App, outside the view tree) feeds `LyricsModel.update(playback:settings:)` on every poll and lyrics-settings change.
- **Two now-playing signals:** `NowPlayingService.track` goes nil on pause (unchanged, drives `TrackOverlay` and `AudioFrame.trackId`). `NowPlayingService.playback` is a Combine subject (NOT `@Published`, so a poll never re-evaluates a view) carrying a `PlaybackSnapshot` that stays populated while paused; lyrics use only this one, so a pause freezes the lyrics and resume does not refetch. It is only read and sent while lyrics are enabled (`setLyricsEnabled`); with lyrics off the poll does no extra player reads **except** a play-position read for restart detection (below).
- **Restart detection (`replayNonce`):** every poll reads the active player's position; when the same track jumps back to the start (replay, repeat-one loop, or a seek to the beginning — position drops below ~2 s after having been past ~3 s), `NowPlayingService` bumps `@Published replayNonce`. Both the track overlay and the lyrics header fold it into their `.task(id:)` so a restart re-shows the title (track card re-blooms; no-lyrics header reappears) without a real track change. This is the one extra player read the poll now does even with lyrics off.
- **Spotify trims its reported duration under Crossfade:** the scripted `duration` is the length Spotify will actually PLAY — with Crossfade on, a song queued into another reports its true length minus the blend (measured on "Audition": 228.267 s true; 216.267 s with a 12 s crossfade; 205.185 s inside a playlist), and it can change mid-song. Lyrics are matched by length, so a trimmed value picks a record for a different cut. `NowPlayingService.trueLengthMs` corrects it at the source for Spotify: `TrackLengthMemory` (Core, tested) keeps the longest length seen per track id, and `SpotifyTrackLengthFetcher` reads the published length (`music:duration` meta, whole seconds) from `open.spotify.com/track/<id>` once per track per session (streamed, stops at the tag, ~15 KB; sends only the track id; failure = reported length as before). `SpotifyTrackPage` (Core) holds the pure id/markup parsing. `--lyrics-probe` prints reported vs published length. Unofficial page: if Spotify changes it, only this correction is lost.
- **English lyrics are cached too** (exact matches only, `en` empty): a repeat play needs no lookup. The cache-load path shows them single-column via the detector; an all-empty-`en` entry that no longer reads as English is refetched rather than shown with a blank translation column.
- **Units:** Spotify's scripted `duration` is MILLISECONDS (measured; its dictionary says seconds). Music's is seconds. `player position` is seconds for both. Convert only through `PlaybackUnits`.
- **Stale results:** every await in `LyricsModel` re-checks a generation counter; a fetch or translation that finishes for a track that is no longer current is dropped. Keep that check when adding await points.
- **Never** put original text in the translation column. A failed translation leaves `LyricRow.translation` nil and writes nothing to the cache.
- **User data:** cache at `~/Library/Application Support/MacVisualizer/lyrics/<sha256>.json` (keyed by normalized title, artist, album, whole-second duration), key at `.../gemini-key` (0600). Neither goes in the repo, `settings.json`, or logs. Never log lyric text or the key. `GeminiKeyStore.write("")` with a blank value DELETES the key file; the Settings "Clear" button confirms first so a stray click can't wipe it.
- **Not captured by the render probe:** the overlay is SwiftUI, so it must be validated in the live window.
- **Sandboxed shells:** if `make build` fails with "cannot execute tool 'metal' due to missing Metal Toolchain" while `xcodebuild -showComponent MetalToolchain` says installed, run make with `TOOLCHAINS=<Toolchain Identifier from that command>`.

## Spinner

The 25th and 26th styles are the two Spinners (see "Two Spinner styles" first): the Disc Spinner is a machined-metal two-sided disc (fidget-spinner-style puck) you spin with the scroll wheel, a lit 3D object with a hub mark on each face, glow rods, a knurled rim and a soft shadow. It stays visible while it spins. It has two renderers: **RealityKit (the default on macOS 15 and later)** and the classic fragment-shader renderer (the stand-in while RealityKit loads, the fallback below macOS 15, and the alternative selected with `g`). Both styles are hidden below macOS 15 (see "macOS 15 gate"); the deployment target stays 14.4. All Spinner code is original work (no third-party code; THIRD_PARTY_NOTICES.md needs no Spinner entry, and the Tri-wing model has an inspiration-only entry in NOTICE).

- **Two Spinner styles.** The Spinner is two ordinary styles in the normal rotation: **Disc Spinner** (`.spinner`, raw value `"spinner"` unchanged, formerly "Spinner") and **Tri-wing Spinner** (`.triWingSpinner`, raw value `"triWingSpinner"`, appended last). `h` / `l`, random, the per-style Enabled toggle, the right-click menu and the Settings style list treat them separately; both carry the macOS 15 gate. Everything that means "a spinner is active" tests `VisualizerStyle.isSpinnerFamily` (scroll wheel, keys, Option-drag and the window lock, hum, presence, RealityKit setup, `MetalRenderer`, the cheat sheet, the Settings sections), never `== .spinner`. **The drawn body comes from the STYLE** (`spinnerModel`), not from a setting: `SpinnerSettings.model` is kept only so old files decode (it is the migration input) and is pinned to the style by the decoder; nothing reads it to choose what to draw, and `VisualizerSettings.spinnerSettings` returns a copy with `model` set from the style. Each style has its own `StyleProfile` and so its own `spinner` settings. **Which profile is read:** `settings.spinnerSettings` = the active spinner style's profile (the Tri-wing Spinner also forces `renderer = .realityKit`: its saved renderer is ignored and `g` does nothing there); anything that runs in every style (the hum player) uses `settings.spinnerSettings(lastActive:)`, which falls back to the spinner style most recently active (`MetalView.Coordinator.lastSpinnerStyle`), else the Disc Spinner, via the pure `SpinnerProfileSelection.style(active:lastActive:)`. **Shared spin state:** both styles' `SpinnerVisualizer`s are built with `SpinnerSharedState.shared` (`VisualizerStyle.makeVisualizer()`), which holds `physics` (angle, speed, the direction lock), `orientation` (pitch and yaw with targets) and the last-advance clock, so `h` / `l` between the two carries the spin and pose over; a standalone `SpinnerVisualizer()` (tests) owns a private state. Everything else (settings, music drive, light pulse) is per style. **Tri-wing Spinner is RealityKit only:** while RealityKit loads its scene is EMPTY (no shader stand-in; `MetalRenderer.encodeShaderFill` skips the shader pass) and then fades in with the usual `mix` crossfade; if RealityKit setup fails (`RealitySpinnerHost.state == .failed`) the disc shader is drawn instead so the window is not blank, and one `spinner-render` line is logged (`Log.spinnerRender`). RealityKit builds both bodies in one setup and `applyModel` switches them by enabling groups, so `h` / `l` between the two styles does not rebuild; the model in `RKFrameParams` and the at-rest reuse key comes from the active style. **Keys:** `spinnerKeyAction(..., style:)` knows the style: `c` (hub finish) and `g` (renderer) are Disc Spinner only; `e` (edge lights) and Shift+`m` (plate metal) are Tri-wing Spinner only; `m`, `t`, `y`, `0`, `b`, `u` and Option variants are shared; there are no model keys (`s` / Shift+`s`) and no "Next Spinner" menu item. **Settings panel:** `SpinnerSettingsSections(model:style:)` shows only what applies: the Disc Spinner has no Edge lights, Lights follow the beat, Resting glow, Beat glow, Light colours, Combination, Plate metal or Boss metal; the Tri-wing Spinner has no Hub finish and no Renderer section (it has an Orientation section with Reset orientation); no Model picker in either. The `?` cheat sheet lists the keys valid for the active style (`CheatSheetOverlay.spinnerStyle`). **Migration (in `VisualizerSettings.init(from:)`, also used for `user-defaults.json`):** a file with no profile for `.triWingSpinner` gets a COPY of the Spinner's profile (every field including Enabled and the Spinner settings); if that file was showing `.spinner` with the Spinner's stored `model == triWing`, the active style becomes `.triWingSpinner`; a file that already has the profile is left alone; then the stored `model` is pinned (`.disc` on the Spinner profile, `.triWing` on the Tri-wing's, which is also what `StyleProfile.defaults(for: .triWingSpinner)` carries). After the copy the two profiles are independent. `SettingsBaseline` needs nothing special: the baseline for the new style is the snapshot's migrated profile, else `StyleProfile.defaults(for:)`. The render probe still accepts `spinner ...,g1,d1` (routed through the Tri-wing Spinner style) and also the style name `triWingSpinner` (RealityKit forced).

- **Renderers.** The persisted `SpinnerSettings.renderer` defaults to `.realityKit`; `SpinnerRendererChoice.effective(realityKitAvailable:)` resolves to `.shader` before macOS 15. - **Setup phases and load time.** (1) Background queue: `buildPuckCPU` (mesh arrays) and `makeAllImages`, whose jobs (face textures 2048, smeared face textures 1024, web opacity 1024 + arc textures, environment equirect 1024x512; the hub marks are no longer textures, see below) now run ONE AFTER ANOTHER because each already spreads its rows over every core with `concurrentPerform`; running the jobs concurrently on top of that over-subscribed the cores (about 1.7x slower, measured). (2) Main thread, `RealitySpinnerRenderer.build`, async with a `Task.yield` whenever a step has run more than about 3 ms so the app keeps drawing: texture resources, environment resource, part meshes, arc meshes + materials, scene assembly. Per-phase timings are appended to `RealitySpinnerHost.setupLog` (the probe prints them); `maxMainStepMs` records the worst main-thread step. A failure sets `state = .failed` and `failure`, and the shader stays on screen. **Measured in Debug on an 8-core Mac (CPU generation, before to after):** hub textures (since REMOVED, see "Metals, finishes, marks") 8.4 s and 12.8 s to 0.15 s and 0.20 s, then 0.21 s and 0.28 s in the last measurement before the removal; face textures 7.9 s to 0.82 s; smeared face textures 2.4 s to 0.25 s; environment 3.7 s to 0.49 s; mesh arrays 3.7 s to 0.7 s; web opacity + arc textures 1.7 s to 0.14 s; all CPU generation 12.8 s to about 2.0 s; total setup wall time 13.7 s to about 3.3 s (the rest is main-thread RealityKit resource creation). What changed: (a) the hub marks used to be fast signed-distance textures; they are now real geometry built on the CPU (`HubCutMesh`, 60 to 120 ms per hub in Debug, inside "CPU mesh arrays", logged as "hub cut meshes F/B"), and `RKHubReference.swift` and `--rk-hub-check` were deleted with the textures; (b) `SlitGeom.nearest/within` prune with per-block bounding circles instead of scanning 700 segments (the web mesh took 3.7 s; the result is identical); (c) `pocketSDF` has no per-pocket trigonometry and skips pockets that cannot be nearest; (d) the environment rows run in parallel. **Debug-build gotcha:** `@_optimize(speed)` does NOT specialise standard-library generics in a Debug build, and closure literals are not covered at all, so hot per-pixel code must avoid `min`/`max`/`abs`/`UInt8(clamping:)`/`for … in 0..<n`/array or struct-of-arrays copies/`SIMD` arithmetic: use the concrete helpers in `RKFastMath.swift` (`rkMin`, `rkMax`, `rkAbs`, `rkClamp01`, `rkClampByte`), `while` loops, raw pointers, and put row work in local `@_optimize(speed)` functions passed to `concurrentPerform(iterations:execute:)` instead of closure literals. `sample <pid>` on a running probe shows the generic-witness frames when this regresses.
- **Region render target (RealityKit).** The RealityKit target is a **square region centred on the puck, not the whole window.** Half of its side is `RealitySpinnerRenderer.regionHalfSide(distance:spread:)` puck radii (R) = 1.06 + 0.15 x shadow distance + 0.09 x shadow spread, which is exactly 1.3 at the defaults (the body stays inside 1.013 R, perspective at camera distance 8.6 R grows that to about 1.03 R; the cast shadow sticks out by about 0.15 R per unit of distance; blur adds 3 sigma = 0.09 R per unit of spread); at the largest settings it grows to about 1.7 R so puck plus shadow stay inside the target. Distance and spread are quantised to 1/20 so a slider drag does not retarget on every tick. The puck's size setting changes only `pxPerR` (the on-screen size of R), so the region follows it. The side is rounded up to a multiple of 16 (`renderSideGranularity`) and capped at `maxRenderSide` = 1536 px; **below the cap one texel is one screen pixel**, above it the copy pass scales up. The camera's field of view is set from the region's world side (`setFrameWorldSide`). Targets (a ring of 3 output slots plus the half-size shadow textures) are re-created only when the rounded side changes. The copy pass (`rk_copy_fs`, `RKCopyUniforms`: `sceneSize`, `regionOrigin`, `regionSize`, plus shadow opacity/use flag) places the region in the scene texture at the puck's position (window centre plus the content offset, snapped to whole pixels), so **moving the puck (lyrics offset) only changes the copy rectangle and never reallocates**. When fully RealityKit (`mix >= 0.999`) only that rectangle is drawn (scissor).
- **At-rest reuse.** A resting spinner reuses the previous output and shadow: no RealityKit render, no shadow passes, no wait on RealityKit. The reuse key is target side, framing (world side), pitch, yaw, spin, omega, metal, hub finish, hub roll, glow, room light, spin blur and the quantised shadow distance and spread; the region position is deliberately not part of it (shadow darkness only changes the copy uniform, so it is not either).
- **Compositing and sync (RealityKit).** `RealitySpinnerRenderer.encodeFrame` renders the puck alone into a premultiplied rgba16Float texture with `updateAndRender`, whose actions signal the shared event `rendered` with an increasing sequence number (and, before the render, wait on `consumed` when the slot was still being read). The app's own command buffer then `encodeWaitForEvent(rendered)`, runs the shadow passes, and `rk_copy_fs` copies the puck into the scene texture (premultiplied source-over, or a blend-colour lerp by `mix` during the crossfade), after which the command buffer signals `consumed` with the frame number. Per output slot, `slotRead` holds the latest frame whose copy reads it, so a fresh render into that slot waits for it. Bloom, trails and the rest of the post chain then apply as for any style. The scene alpha channel carries the spinner's coverage (`perPixelAlphaMode == 2`), so a transparent window shows through around the object.
- **Shadow by difference (RealityKit, opaque and transparent modes alike).** A ground plane lit only by a dedicated shadow light, nearly on the view axis (the key light lights the puck only), is rendered with and without the puck at half the target size (the ground-only renders are cached per target size/framing); `rk_shadow_cov_fs` turns the pair into a coverage (the puck silhouette translated 0.06 R right and 0.09 R down underneath it), an `MPSImageGaussianBlur` with sigma `shadowSigmaInR` = 0.029 R (in half-resolution pixels, quantised to 0.25) softens it, and `rk_copy_fs` composites it as black alpha over the scene. The blur object is recreated only when the quantised sigma changes. No ground has to match the background colour. **Settings:** darkness is the copy pass's `shadowOpacity`; distance scales both the shadow light's horizontal direction (the static ground renders are keyed by the quantised distance and redone when it changes) and the translated-silhouette offset (0 puts the shadow directly behind the puck; the 3x3 coverage search then leaves a thin dark edge, a known limitation); spread multiplies the blur sigma.
- **Spin blur.** Speed-dependent: the shader sweeps the disc over the frame's `frameDt` (motion-blur loop); RealityKit cross-fades to smeared overlays and arc meshes between `blurLo` (2 rad/s) and `blurHi` (25 rad/s) in `applyBlur` (arc level from speed x shutter time). The **Spin blur** setting multiplies the sweep (shader `u.spinBlur`) and the speed fed to `applyBlur` (RealityKit, so the ramp and shutter scale together); 0 means no sweep, no overlays and no arcs at any speed; the arc level saturates at `arcLevels - 1`.
- **Physics and input.** `SpinnerPhysics` (Sources/Core, pure): angle/velocity, Coulomb + viscous friction, the live speed limit is `SpinnerSettings.topSpeed` (`SpinnerTuning.maxSpeed` 60 is only the default and the hum's normalisation), optional detents (off; `SpinnerTuning.detent*` are test knobs). The friction multiplier scales BOTH friction terms (Coulomb and viscous) together with the music drive's sustain scale; the push multiplier scales `impulseGain`. **Direction lock (setting, default on):** the push that starts the disc from rest sets the direction; an opposing push only brakes and cannot restart it the other way until `restartLockoutSeconds` of quiet. `SpinnerInput.shared` carries the scroll impulse from the wheel monitor (`InputController`; the bare wheel spins the disc while the Spinner is active and the event is NOT consumed) to the visualizer (`impulseGain`, 1.5 rad/s per notch at push strength 1). **Scroll-direction rule:** the wheel pushes the same way on screen on either face, so `SpinnerVisualizer.advance` negates the impulse while `orientation.facesViewerFront` is false. With **Direction lock off** an opposing push simply adds (passes through zero and reverses, no lockout, the pre-lock behaviour).
- **Orientation (`SpinnerOrientation`, Sources/Core, pure).** Two unwrapped angles, **pitch** about screen-x (positive tips the top edge away from the viewer) and **yaw** about screen-y (positive turns the right edge away), **yaw applied after pitch in screen space** (R = Ry(yaw) * Rx(-pitch); the RealityKit transform uses exactly this product). Key steps move the TARGET by the `rotationStepDegrees` setting (5, 10, 15, 30 or 45; 15 gives 24 stops per turn, including exact face-on and edge-on; every choice divides 90, so exact face-on and edge-on stay reachable); the current value eases toward it with `tiltTimeConstant` (0.35 s, first order, no overshoot); a value is reduced to one turn only when sent to a renderer. `facesViewerFront` is `cos(pitch) * cos(yaw) > 0`, keeping the last face when exactly edge-on so the scroll sign cannot flip-flop. `reset()` eases both targets to the nearest whole turn (the shortest way). `resetOrFlip()` (key `0`) and `resetOrFlipYaw()` (Option+`0`) decide from the TARGETS (not the eased values; eps 1e-3 rad): a standard face-on pose is pitch target AND yaw target each a multiple of 180 degrees (`targetIsFaceOn`), so flips by either key chain in any order; there `0` does pitch target += pi and Option+`0` does yaw target += pi (the `y` direction, a flip about the vertical axis; the classic shader ignores yaw, so there it only changes the scroll-direction side); pitch (the `t` direction, so the disc tumbles through edge-on over the usual 0.35 s easing; roughly 1 s to settle visually); anything else -> `reset()`. A second press during the reset animation therefore flips. Carried by `SpinnerOrientationRequests.resetOrFlip` (the Settings "Reset orientation" button keeps the plain `reset`). Rotation steps are unwrapped, so a target far ahead of the current value (key repeat) just eases toward it and settles ~0.35 s after the last step. **Option-drag** (`SpinnerDragGesture`): horizontal movement changes yaw, vertical changes pitch (the surface under the pointer follows it), `dragDegreesPerPoint` = 0.5; movement below a 4-point travel threshold is held back and released once crossed; a drag **nudges current and target together** (`nudge`), so there is no easing lag. Requests from keys and the drag are collected in `SpinnerInput.shared.pendingOrientation` (`SpinnerOrientationRequests`) and drained once per frame by `SpinnerVisualizer.makeVertices`. The old 16 pitch presets (`tiltPresets`, `cycleTilt`) no longer exist. **The classic shader renderer shows pitch only and ignores yaw** (a documented limitation; the scroll-direction rule still follows the full orientation).
- **Self-levelling hubs (`SpinnerHubRoll`, Sources/Core/SpinnerOrientation.swift).** Each hub button turns about the puck's own axis, so every frame the two hub dome entities (`RealitySpinnerRenderer.domeEntities`) are rolled by `SpinnerOrientation.hubRoll` about the puck's z axis so the mark's up points to screen-up. Convention: R = Ry(yaw) Rx(-pitch); the hub-local x and y axes land on the screen at (cos yaw, 0) and (-sin yaw sin pitch, cos pitch), whose determinant cos pitch cos yaw is the front normal z; the roll solves M (-sin t, cos t) ~ (0, 1): t = atan2(-sin yaw sin pitch, cos yaw) when det > 0, and the negated direction when det < 0. Front and back hubs share ONE roll: the back mark's stroke list is authored mirrored in x (`hubPieces(mark:backDome:)`), which is what a face seen from behind needs, so the same in-plane rotation levels either face. The roll is continuous while a face is visible; the unavoidable 180 degree flip happens exactly as det passes through zero (both faces edge-on, invisible); at |det| < 1e-6 the previous roll is kept (`SpinnerOrientation.updateRoll` carries it). The hub parts are real geometry lit by the scene's lights, and they are rolled together so the mark's up always matches screen-up, so the upper-left light convention holds at every pose (verified in stills at (0,0), (180,0), (0,180), (180,180), (135,45), (45,60), (60,-45), (225,0) in both finishes; the classic shader draws its hub upright in the view frame and agrees with RealityKit at pitch 0, 45, 135, 180, 225 and 315).
- **Option-drag plumbing.** `InputController` consumes a left press with exactly Option while the Spinner is active (plus `leftMouseDragged` / `leftMouseUp` monitors), so it does not reach anything else. **Consuming the event does NOT stop the window moving:** background/title-bar dragging (`isMovableByWindowBackground`, transparent title bar) is started by the window server from the window's drag regions, independent of the app's event stream, so the window itself is locked beforehand. `spinnerWindowLocked(spinnerActive:modifiers:dragInProgress:)` (Core, tested) is true while the Spinner is active and exactly Option is held, and for the whole drag once one started (Option released mid-drag stays locked until mouse-up). `InputController.updateWindowLock` re-evaluates it from a `.flagsChanged` monitor and from every key/mouse/scroll monitor event (covers style changes), reading live `NSEvent.modifierFlags`; it sets `isMovable` and `isMovableByWindowBackground` false (saving `isMovable`) and restores them on unlock. `MainWindow.dragLocked` is the shared flag: `configureWindowBackground` sets `isMovableByWindowBackground = !MainWindow.dragLocked`, so a settings refresh cannot re-enable dragging mid-lock. Main-window resign-key and app deactivation cancel the drag and unlock, so a missed Option-up cannot leave the window stuck. Validate live. If the app-wide `mouseControlModifier` is also Option, its left-click binding (previous visualization) is deferred and fires on release only if the press never became a drag (`gesture.rotating` false).
- **Music drive.** `SpinnerMusicDrive` (pure, fed once per frame): mode `off` (default) / `sustain` (removes up to `musicSustain` = 85% of friction at full music level) / `kick` (impulse of `musicKick` = 2 rad/s per full beat) / `both`; all three are settings, and `b` cycles the mode.

A new gate starts with the timer at 0 (launch grace). The old loudness-proportional duck (`SpinnerHumDuck`, `humDuck*`) is gone. A failed start discards the graph, builds a new engine on the next attempt (every 5 s) and logs once per failure streak (category `spinner-hum`); the source is connected at the output device's own sample rate, and a device with no valid format is treated as a failed start. Toggle with `u`. Output only: no extra entitlement is needed (the app is not sandboxed). The hum cannot be verified by tests or the probe: validate it live.

- **Metals, finishes, marks.** `SpinnerMetal`: steel, brass, copper, black zirconium, anodized titanium. **Anodized titanium's colour-shifting film exists only in the shader; RealityKit draws plain titanium grey** (`rkMetals["titanium"]`, a cooler, darker F0 than steel; `RealitySpinnerRenderer.metalNames` index 4; a coloured `sheen` lobe was tried and only darkened the metal, so there is no credible film in `PhysicallyBasedMaterial`). `SpinnerHubFinish`: `lit` (polished hub, the mark cut in as a channel with a glowing floor), `raised` (plain hub, the mark standing proud) and `engraved` (index 2, UNLIT: the mark cut into the polished hub as a dark matte channel). **The RealityKit hub marks are REAL GEOMETRY, not textures** (the classic shader still paints its marks analytically). `HubCutField`/`HubCutMesh` (Sources/Core/HubCutMesh.swift, pure, unit tested in `HubCutMeshTests`) takes the mark as capsule strokes (`hubPieces(mark:backDome:)` in RKTextures.swift, the same lists the shader's marks come from; back mark authored mirrored in x), samples the signed distance on a Cartesian grid (`hubCutCell` = 0.0033 R, a stroke is 6 to 8 cells wide) over the mark's bounding rectangle, finds each outline crossing on the grid edges with a linear estimate plus 4 regula-falsi steps on the true distance (vertices sit on the real outline; the crossing parameter is clamped to 0.02...0.98 so no triangle collapses), and meshes marching-squares cells with the saddle case decided by the cell-centre sample. Every outline vertex exists once per grid edge and is shared by the face polygon, the floor polygon and the wall quad (walls get their own copies at the same position with horizontal normals from the distance gradient, so round caps shade round); winding is fixed from vertex normals and no triangle is ever dropped (a dropped sliver would be a pinhole). The face outside the mark reaches the rim circle through 6 radial rings of quads hung on the rectangle's boundary vertices; the rim points are returned so the chamfer and side wall (`hubRimMeshes`) are built on exactly the same vertices, and ALL hub parts (face, cut, raised mark, chamfer, wall) sit in `domeEntities` and are rolled together, so nothing cracks at any roll. Heights follow the dome profile: floor = dome - `hubCutDepth` (0.014 R, about 4.2% of the hub radius 0.33 R: deep enough that the wall reads, shallow enough that the floor is not hidden at 45 degrees pitch; an earlier spike's 6% hid the floor and 2% was barely visible), raised top = dome + `hubRaiseHeightGeo` (0.008 R, 2.5%); the back hub is the same mesh mirrored in z. ## Settings UI

`SettingsView` is a `NavigationSplitView` (left sidebar + detail form), not the old single scrolling form.

- **Scope split.** The sidebar has a **Global** section (app-wide categories: Styles & Presets, Palette Cycle, Post-FX, Analysis, Track Overlay, Lyrics, Layout, Window) and a **per-visualization** section headed by the active style (Controls first, then Appearance, Glow, Bands). `SettingsCategory` (enum at the bottom of `SettingsView.swift`) carries each category's title, SF Symbol, scope (`isGlobal`), and `allOrdered` sidebar order; `detailSections` switches on the selection to render that category's `@ViewBuilder`. Track overlay, always-on-top and frame rate are under Global (app-wide). The **Layout** category holds the app-wide Center-below-lyrics toggle and the Position sliders, which are PER-STYLE (the section title names the current visualization; lyric position/lines/text size also move the viz, noted in a caption).
- **Rows are plain `Button`s** (`SidebarRow`, a small view with its own `@State hovering`), NOT `List(selection:)` — the List/NavigationSplitView selection mechanism did not respond to the mouse here, so the row sets `selection` itself. Each row fills with the accent when selected and tints on hover, and shows its ⌘-number. **Keep this pattern** if you touch the sidebar.

### JSON backward compatibility for settings

When renaming `StyleProfile` or `VisualizerSettings` fields, preserve old JSON keys via CodingKey raw values. Example: when `siri` was renamed to `ribbonWave`, the enum case kept `rawValue = "siri"`:

```swift
case ribbonWave = "siri"
```

CodingKeys for settings fields likewise:

```swift
case ribbonWaveCount = "siriWaveCount"
```

Old `settings.json` files load cleanly; new code uses the new names.

### Access path for per-style settings

Per-style settings live on `StyleProfile`. Access via `settings.current.<field>`, mutate via `settings.mutateCurrent { $0.<field> = newValue }`. The forwarding properties on `VisualizerSettings` (like `settings.gain`) exist for common fields and proxy to `settings.current.<field>`, but render-mode fields (`voronoiRenderMode`, `heightfieldRenderMode`, `lavaLampRenderMode`, `voronoiShapeMode`) are NOT forwarded — access them via `settings.current.X` only.

### Tolerant Codable for settings

Both `VisualizerSettings` and `StyleProfile` use `decodeIfPresent + default` everywhere. Adding a new field never breaks decoding; old JSON missing the field gets the default value. Pattern:

```swift
let newField = try c.decodeIfPresent(NewType.self, forKey: .newField) ?? d.newField
```

## How to add things

### A new vertex-emit visualizer style

1. Create `Sources/Core/MyStyleVisualizer.swift` conforming to `Visualizer` (license header, `public final class`, `init()`, `makeVertices(...)` returning `[BarVertex]`).
2. Add the enum case to `VisualizerStyle` (preserve positional ordering for tests; case raw value can be omitted or set to a stable string for JSON compat).
3. Update the `VisualizerStyle` switches: `displayName`, `usesRoundParticles` (false unless emitting circular particles), `customShader(settings:)` (return nil unless any render mode is shader-driven), `makeVisualizer()`.
4. Write tests in `Tests/CoreTests/MyStyleVisualizerTests.swift` (license header, `@testable import MacVisualizerCore`, vertex bounds, determinism, beat consumer if applicable, stereo split if applicable).
5. `make test` should still pass (existing `testAllCases` will need to know the new count; the style-count test in `VisualizerStyleTests` (`testCaseCountIsTwentySixAndTriWingSpinnerIsLast`, which asserts 26 cases with `.triWingSpinner` last) and the wrap-around tests (`next`/`previous`) need the new last case).
6. Attribution: if the style was inspired by existing work, add a `NOTICE` entry; if any code was ported, add a `THIRD_PARTY_NOTICES.md` entry with license text (see "Attribution policy").

### A new fragment-shader visualizer style

1. Steps 1-2 above, but `makeVertices` returns `[]`.
2. Add a case to `ShaderKind` (Sources/Core/ShaderKind.swift).
3. Add the fragment shader to `Sources/Rendering/Shaders.metal` (use existing `voronoi_fs` / `lavalamp_fs` as templates; remember `in.uv.y = 0` is at screen TOP per `fullscreen_vs`).
4. Add a uniform struct if your shader needs more than the standard `ShaderInputs` + `PaletteUniform`. Use fixed tuples + `withUnsafeMutableBytes` — Swift `Array<SIMD4<Float>>` inside a struct does NOT survive `setFragmentBytes`.
5. Add a pipeline state property on `MetalRenderer` + create it in `init?` (rgba16Float color attachment).
6. Wire `case .myShader:` in BOTH `encodeShaderFill` AND `renderWithTrails` (they have parallel shader dispatch paths).
7. Update `VisualizerStyle.customShader(settings:)` to return `.myShader` when the active mode demands it.
8. If the visualizer holds stateful uniforms (like `LavaLampVisualizer`'s point positions), the renderer accesses it via the cached `activeVisualizer: Visualizer?` reference set by `MetalView` before each frame.
9. Attribution: if the shader was ported from existing work (e.g. Shadertoy), verify the source license is permissive BEFORE porting, then add a `THIRD_PARTY_NOTICES.md` entry with the full license text and an inline credit header in `Shaders.metal`. Inspiration-only concepts get a `NOTICE` entry instead (see "Attribution policy").

### A new top-level setting

1. Add the field to `VisualizerSettings` struct (with init parameter + assignment + default).
2. Update `static let defaults`.
3. Add to `CodingKeys` enum.
4. Add to `init(from decoder:)` using `decodeIfPresent ?? d.<field>`.
5. Add to `encode(to:)`.
6. Add UI in `Sources/App/SettingsView.swift` (typically Tweaks tab or a new section).
7. Add round-trip + legacy-JSON-without-field tests in `VisualizerSettingsTests.swift`.

## Audio capture

`AudioCaptureService` (Sources/Services) taps **every running target player at once** (Spotify AND Apple Music) via a Core Audio process tap and bridges it through a private aggregate device clocked to the **default OUTPUT device** — `CoreAudioHAL.defaultOutputDeviceUID` reads `kAudioHardwarePropertyDefaultOutputDevice` (where the music actually plays), NOT `DefaultSystemOutputDevice` (the system-alert output, which can be a different device).

- **Tap all players, not one:** a paused/silent player contributes nothing to the stereo mixdown, so capturing every running target means switching players (or one app taking over from the other) needs **no re-selection and no rebuild** as long as both were present when the tap was built. `ProcessLocator.allTargets` returns the process-object ids of all running targets; `TargetProcessSelection.select` (Sources/Core, pure, unit-tested) is the id-set picker. The service listens for process-list changes and rebuilds only when the **set** of running targets changes (a player launches or quits) — NOT per track or per play/pause.

Two more mechanisms keep capture alive across output-routing changes — notably **Bluetooth**, which changes the default output device and sleeps its clock between tracks:

- **Route-change listener:** the service listens on `kAudioHardwarePropertyDefaultOutputDevice` and rebuilds the tap/aggregate on the new device when the UID differs from the one it was built with (`builtWithOutputUID`). Installed once, removed on stop/deinit; the rebuild hops to **main**, where every lifecycle call is serialized.
- **Stall watchdog:** `CaptureStallMonitor` (Sources/Core, pure, unit-tested) decides when a *running* capture that has stopped delivering frames should be rebuilt — after `stallSeconds` with no sample, no more often than `rebuildBackoffSeconds`. `RenderModel.tickCaptureWatchdog` (called every frame from `MetalView`, main thread) drives it off `box.recent` and calls `capture.restart()`. This is the backstop for stalls with **no change event** (a Bluetooth clock pausing). **A `.failed` capture is retried too:** a transient Core Audio error during a rebuild (e.g. `CreateProcessTap` returning no tap) used to leave `.failed` terminal, so the scene stayed faded out until relaunch. The monitor takes a `CaptureStallMonitor.Status` (`running`/`failed`/`other`) and retries `.failed` every `failedRetrySeconds` (5 s, so a permanent failure like denied permission does not hammer Core Audio); `.stopped` and `.noTargetProcess` are never retried by the watchdog. The default-output-device listener also rebuilds from `.failed` (regardless of `builtWithOutputUID`), and `start()` treats a tap id of `kAudioObjectUnknown` as a failure ("CreateProcessTap returned no tap"). **Clocks and gate:** the rebuild is synchronous on main and can take seconds, so the caller reports completion with `noteRebuildFinished(now:)` (fresh `CACurrentMediaTime()` taken after `restart`, and after the launch `start`), which restarts the stall, backoff and failed-retry clocks from the finish time; without it the next frame re-fired at once. Stall rebuilds back off `rebuildBackoffSeconds * 2^(n-1)` for n rebuilds since the last sample, capped at `maxRebuildBackoffSeconds` (60 s; any sample resets n, so a genuine mid-playback stall still gets the fast 1.5 s + 3 s response). `shouldRebuild(playerPlaying:)` suppresses stall rebuilds while no track is playing (`RenderModel.currentTrackId == nil`, fed by the 1.5 s now-playing poll; a tap built while stopped delivers no frames, so rebuilding only storms); `.failed` retries are not gated, and the stall clock restarts when playback resumes.

**Lifecycle off main:** every Core Audio lifecycle call (tap/aggregate/IO-proc create, start, stop, destroy, `startBody`'s property reads, listener install/remove, `ProcessLocator` queries) runs on ONE serial queue, `com.edespino.MacVisualizer.capture-lifecycle`, because a slow audio service blocks single calls for 30 s (measured: 90 s at launch). **Invariant: lifecycle state (tap/aggregate/IO-proc ids, `builtWithOutputUID`, listener blocks, `lifecycleState`) is touched only on that queue**; never `DispatchQueue.main.sync` from it. `start`/`restart`/`stop` only enqueue. `CaptureRequestQueue` (Core, tested) coalesces: at most one operation waits behind the running one, latest request wins, so a burst of listener events during a hang is one rebuild; a stop replaces a pending start (and a later start replaces the stop). The listeners (non-main queues) decide on the lifecycle queue and call the same coalescing `submit`. `state` is authoritative on the queue and mirrored to main via `main.async` (read `capture.state` on main only); `isStarting` (main) is true while lifecycle work is queued/running. **Completion-driven watchdog:** `start/restart(reason:completion:)` deliver `completion` on main once the covering rebuild finishes (default impl for other conformers: synchronous). `RenderModel` calls `stallMonitor.noteRebuildStarted` when it requests one (launch included) and `noteRebuildFinished` (fresh clock) + `captureState` refresh on completion; `CaptureStallMonitor.shouldRebuild` returns false while a rebuild is in flight, however long. `deinit` tears down synchronously on the queue (queue-specific key avoids a self-deadlock). **Diagnostics:** every request logs `Capture start: reason=… previousState=… targets=…` and `Capture start total: N ms` (category `audio-capture`), coalesced or skipped requests are logged, and `AudioCaptureService.timed` logs any single Core Audio call over 50 ms as `Capture slow call: <name> N ms` (the buffer property reads are timed the same way). Filter with `log stream --predicate 'category == "audio-capture"'`.

Without these, `IdleFadeTracker` sees `.noCapture` and idle-fades the whole scene (and lyrics) out while audio is actually playing — the "coming and going" symptom. `restart()` is on the `AudioCaptureSource` protocol (default `stop(); start()`; the real service overrides it to reuse its idempotent `start()`, so the output-device listener survives the rebuild).

## Foundation services (Cluster A)

- **Beat detection:** `frame.beat` is `true` on the single frame an onset fires; `frame.beatIntensity` is the magnitude in 0…1 on that frame only. Self-tuning via goom2k4-style adaptive threshold. To consume in a visualizer, watch `frame.beat` and decay your effect with a `realDt`-based half-life (so the beat boost doesn't depend on `particleSpeed`). The **lyric shadow bounce does NOT use this detector** — it has its own `LyricBeatFollower` fed `frame.bassEnergy` (see "Lyrics overlay"), because `BeatDetector`'s 0.05 floor sits above the user's capture level.
- **Stereo path:** `frame.bandsLeft` and `frame.bandsRight` are always populated. For mono sources, `bandsLeft == bandsRight == bands`. Visualizers opt in to using them by checking `settings.useStereoImage`. Conventional split: cells/seeds with x<0 use bandsLeft, x≥0 use bandsRight.
- **Track ID:** `frame.trackId` is `"title|artist|album"` or nil. Used by Voronoi's `perTrack` shape mode for reshuffle-on-track-change.

## Accumulated gotchas

- **Metal buffer layout:** `Array<SIMD4<Float>>` inside a Swift struct breaks `setFragmentBytes`. Use fixed-length tuples and `withUnsafeMutableBytes` to populate them. See `VoronoiUniforms.swift` / `LavaLampUniforms.swift` in `Sources/Core/`.
- **SeededRNG scope:** `SeededRNG` is module-internal to MacVisualizerCore. The renderer (Sources/Rendering) cannot import it; use a private `LocalRNG` with identical xorshift64 math when you need deterministic generation in renderer code.
- **Shader UV.y is flipped:** `fullscreen_vs` outputs positions with negated Y, so `in.uv.y = 0` corresponds to screen TOP. If your shader needs NDC convention (+y = top), use `float2(in.uv.x * 2 - 1, 1 - in.uv.y * 2)`. The existing `plasma_fs`, `bumpscope_fs`, `voronoi_fs` use the flipped convention silently because their patterns are symmetric.
- **Test setup ordering:** In tests that change BOTH `visualizerStyle` AND a per-style setting, set `visualizerStyle = .x` BEFORE `mutateCurrent { ... }`. Otherwise `mutateCurrent` mutates the wrong profile (defaults start at `.bars`).
- **`customShader(settings:)` vs `.customShader`:** The render loop uses the settings-aware method. The parameterless `.customShader` property exists for legacy compatibility (returns nil for mode-dependent styles); don't use it in new code.
- **`particleSpeed` coupling:** Several visualizers use `dt * settings.particleSpeed` for physics. Beat-driven boosts should use raw `realDt` (wall-clock) so they decay correctly even when `particleSpeed = 0`.
- **Frame rate:** the app-wide `targetFPS` (Settings > Window) is the default; a style can override it with `StyleProfile.frameRateOverride` (`Int?`, nil = use global; the picker is the first row of each style's Controls; a NEW key, not the legacy per-style `targetFPS`). `FrameRatePolicy.rate` (Core, tested) also returns `idleFPS` (10) once the visualization has been inactive for `idleDelaySeconds` (3 s, past the 2 s fade-out), so an idle window stops loading the GPU/compositor. `MetalView.Coordinator.draw` applies the rate each frame (written only on change); `updateNSView` no longer sets it. The idle check and the capture watchdog run on the draw path, so the idle rate must stay above 0 (never pause the view).
- **Stepped `Slider` tick count:** a SwiftUI `Slider(..., step:)` on macOS lays out one tick-mark slot per step, on every layout of the form it sits in. Particles' "Max particles" was `in: 1...4000, step: 1` (4,000 ticks): the whole Particles Controls panel was sluggish and a drag hung the app with a beachball (main thread 100% in `SliderMarkLabels.LabelLayout.LabelLayoutResolver.place`, found with `sample <pid>`). **Fix/pattern:** for a wide integer range, omit `step:` and round in the binding's setter (`set: { field = Int($0.rounded()) }`). Keep `(max - min) / step` small — the three sliders at 400+ ticks were converted; the largest left are Lyrics Timing offset (201), Voronoi Seeds (128), Lava Lamp Grid size (113), unprofiled. Dropping the step loses visible ticks and exact arrow-key stepping, so a slider that must snap to a coarse unit (Timing offset, 100 ms) needs its rounding kept at that unit.
- **Never use whole-transaction `withAnimation` in a handler that can run during a window resize.** `withAnimation` puts the animation on the whole view-graph transaction. If it runs while the hosting view holds a new size it has not laid out yet (the window border's `updateAuto` is called from `NSWindow.didResizeNotification` and from a timer), SwiftUI animates the ROOT size too and writes each interpolated size back to the window frame, which changes the root size again: a layout loop that AppKit ends with an exception. Scope the animation to the view that changes with `.animation(_:value:)` (the window border fade does: `.animation(mode == .auto ? … : nil, value: level)` on the stroke). Related launch fix: `FramePersistence.attach` (in `WindowConfigurator`) restores the saved frame with `setFrame` and calls `window.layoutIfNeeded()` immediately, so the hosting view takes its new size before the next SwiftUI update carries an animated transaction (track card bloom, lyric scroll). Other `withAnimation` uses (`TrackOverlay`, `LyricsOverlay`) run from tasks and timers, not from resize handlers; keep it that way.
- **Window diagnostics.** `Log.window` (category `window`) logs `Main window frame restore: requested=… actual=… openedAt=…` (`openedAt` is where SwiftUI opened the window before the saved frame was applied) and, from `logWindowIdentity` in `InputController.swift`, `Window identity: role=… number=… ptr=… frame=… contentLayoutRect=… screenVisibleFrame=… views=…` for the main and Settings windows. They exist to identify the window involved in an AppKit layout-loop crash; keep them when touching window code.
- **Command-line probes** (run the binary inside the built app): `--render-probe <out.png> [style] [renderMode] [glow]` (offscreen PNG; Spinner tokens under "Spinner"), `--lyrics-probe`, `--acknowledgements-probe <outdir>` (offscreen PNGs of the Acknowledgements window, 3 sections x light/dark x 720x620 and tall), `--audio-probe`, `--nowplaying-probe`, `--list-audio-processes`. Dispatched in `AppEntry.main` (`MacVisualizerApp.swift`) before the app starts.
- **Bundle ID:** `com.edespino.MacVisualizer` (and `com.edespino.MacVisualizerCore`) in `project.yml`. Confirm the identifier is registered before App Store distribution.
